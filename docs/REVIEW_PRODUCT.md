# 三份塔防草案产品与 PRD 严苛审查

> 审查日期：2026-09-04  
> 审查角色：资深独立游戏制作人 / PRD 审查员  
> 只读输入：`PRD_FRAMEWORK_DRAFT.md`、`TECH_RESEARCH_DRAFT.md`、`ASSET_AUDIO_RESEARCH_DRAFT.md`  
> 审查目标：判断三份草案是否已经足以指导零基础用户与 agent 完成一款可发布的完整单机塔防，而不是在执行中退化成 Demo、教程工程或彼此冲突的半成品。  
> 严重度：**Blocker**＝不解决就不应进入正式生产；**Major**＝不会立即阻止原型，但会显著造成返工、延期或成品质量不足；**Minor**＝局部一致性、表达或维护性问题。

---

## 1. 执行结论

### 1.1 总判定

**当前状态：NO-GO，不应直接进入完整内容生产。**

三份文档并没有把范围缩成 Demo；相反，`PRD_FRAMEWORK_DRAFT.md` 明确提出了 24 个主线关卡、6 座塔、4 名英雄、24 种普通敌人、8 种精英和 6 个 Boss 的完整买断制游戏目标（`PRD_FRAMEWORK_DRAFT.md:30`），并包含成长、难度、教程、存档、成就、无障碍、本地化、测试和发布验收。这一点方向正确。

但三份文档目前描述的**不是同一个游戏**：

- PRD 是“固定路线/建造节点 + 明暮相位 + 六座原创塔 + 四技能英雄 + 24 关完整战役”；
- 技术稿仍是“可放塔堵路/AStar 动态重算 + 传统四塔 + 三档升级 + 流星雨/援军 + 8–12 关 + 无限模式”；
- 资产稿是“通用中世纪地牢、史莱姆、僵尸、坦克、木质卷轴 UI、零散 chiptune”的免费素材集合，没有覆盖 PRD 的潮汐群岛世界、原创塔形、英雄、精英、Boss、章节视觉和中英文字体。

因此当前文档可以指导 agent 做出一个**通用塔防骨架**，但不能可靠指导它完成 PRD 中定义的完整游戏。若现在开工，最可能的结果是：技术原型可运行，后期再花数月推翻路径、升级、内容 ID、UI 与资产，最终因范围与风格债务停在“比 Demo 大、离正式版远”的状态。

### 1.2 可执行成熟度评分

| 维度 | 评分 | 结论 |
|---|---:|---|
| 产品愿景 | 7/10 | PRD 有鲜明机制支柱，但叙事和市场表达尚未冻结 |
| 原创性 | 6/10 | PRD 原创方向较好，技术稿和资产稿正在把它拉回通用/KR 邻近表达 |
| 核心系统闭环 | 7/10 | 战斗闭环完整；跨文档实现规则不一致 |
| 内容设计 | 7/10 | 有 24 关和敌塔英雄名册，但仍是蓝图，不是可直接生产的数据规格 |
| 制作阶段策略 | 6/10 | 纵向切片思路正确；里程碑范围、名称和退出标准未统一 |
| 工期可信度 | 3/10 | 对零基础兼职个人严重偏乐观，且未折算美术、QA、本地化与返工 |

| 事实可靠性 | 4/10 | 技术稿和资产稿存在把推断、社区观点或间接核实写成事实的情况 |
| 发布准备度 | 3/10 | 发布项目清单存在，但离可执行发行计划仍有明显距离 |

### 1.3 值得保留的基础

以下内容不应因本审查而推翻：

1. PRD 的“明潮/暮潮 + 航标充能竞争”是目前最有识别度的原创核心；
2. 24 关四章战役、完整结局、两种首发语言、无障碍与存档可靠性作为完整游戏目标是合理的产品定义；
3. 数据驱动、固定 ID、关卡校验、原子存档、自动化回归和纵向切片方向正确；
4. “先完成发布品质纵向切片，再批量生产后 21 关美术”的门禁非常重要（`PRD_FRAMEWORK_DRAFT.md:1189`）；
5. 资产稿对来源、作者、许可证和不确定状态做了大量记录，可作为候选源数据库继续使用；
6. 技术稿对 Godot 常见模块做了广泛盘点，可作为研究索引，但不能直接当作已批准的技术设计。

# 2. Blocker — 必须在正式生产前解决

## B-01 三份文档没有唯一产品真相，关键范围互相冲突

**证据**

- PRD 的 P0 是 24 关、6 塔、4 英雄、24 普通敌人、8 精英、6 Boss（`PRD_FRAMEWORK_DRAFT.md:30`）。
- 技术稿把完整战役写成 8–12 关（`TECH_RESEARCH_DRAFT.md:1349`、`:1495`）。
- 技术稿只计划 4 种塔、6 种敌人和 2 个升级档（`TECH_RESEARCH_DRAFT.md:1348`）。
- PRD 将无尽模式放在发布后 P2（`PRD_FRAMEWORK_DRAFT.md:32`）；技术稿却多处把“战役 + 无限模式”作为产品结论（`TECH_RESEARCH_DRAFT.md:453`、`:1379`、`:1529`）。
- 技术稿后续步骤引用不存在的旧文件名 `PRD_DRAFT.md`、`ART_ASSETS_RESEARCH_DRAFT.md`、`AUDIO_ASSETS_RESEARCH_DRAFT.md`（`TECH_RESEARCH_DRAFT.md:1537-1540` 附近），实际文档名称不同。

**影响**

Agent 会把任何一份文档当成权威并产生不同实现；内容数量、数据 schema、UI、存档和里程碑都会分叉。零基础用户无法判断冲突时听谁的。

**必须修订**

建立一份 `PROJECT_CANON.md` 或在正式 PRD 首部加入“唯一真相表”，至少冻结：

- v1.0 内容数量；
- 首发/发布后模式；
- 塔等级与模块结构；
- 英雄技能数量；
- 路径与建造规则；
- 货币和术语；
- 首发平台与语言；
- 引擎版本；
- 正式文件名和优先级。

冲突裁决顺序建议：`PROJECT_CANON` → 正式 PRD → 技术设计 → 内容/资产规格 → 研究资料。研究稿不得覆盖已批准 PRD。

**放行标准**

全局搜索以下术语时不存在冲突：`8–12 关`、`4 种塔`、`3 档`、`流星雨`、`援军`、`无限模式`、`Stars`、`gold`、`lives`、`goblin`。如保留，仅能出现在“已废弃方案”章节。

## B-02 路径与建造模型发生根本冲突

**证据**

- PRD 明确排除自由建路（`PRD_FRAMEWORK_DRAFT.md:37`），关卡使用有效建造点，并建议敌人优先沿设计师定义曲线/航点移动（`PRD_FRAMEWORK_DRAFT.md:238`、`:746`）。
- 技术稿设计的是格子建造、塔阻塞道路、每次放塔后 AStar 校验和动态重寻路（`TECH_RESEARCH_DRAFT.md:332-364`、`:413-422`、`:1358`）。
- 技术稿 AStar 初始化示例把 `path_cells` 标记为 `solid`（`TECH_RESEARCH_DRAFT.md:424-440` 附近），从语义上又与“敌人在路径格上行走”冲突。

**影响**

这是地图格式、AI、塔位、相位改道、波次可重复性、性能和关卡平衡的共同地基。两种模型不能在实现中“以后再决定”。

**推荐裁决**

以 PRD 的固定路线为准：

- 关卡作者放置 `BuildNode`，玩家只能在节点建塔；
- 路线由 `PathNetwork` 的稳定 route/segment ID 组成；
- 明暮相位只切换预先设计的边，不做自由动态寻路；
- 敌人记录 `route_id + segment_id + progress`；
- 只有工兵/机关可以切换批准的捷径；
- AStar 只可用于英雄地面移动或编辑器校验，不用于普通敌人每帧寻路，也不用于玩家自由堵路。

**放行标准**

先写出 `PathNetwork` schema、C02 的两相路线图、敌人改道状态迁移和固定种子回归测试；同一波在相同操作下必须复现相同路线与结果。

## B-03 原创性被技术稿中的直接范式复刻破坏

**证据**

- PRD 设计六座原创塔、II 级三选一校准模块和 IV 级技能（`PRD_FRAMEWORK_DRAFT.md:249`）。
- 技术稿仍明确写“弓箭、法师、兵营、炮台”四塔（`TECH_RESEARCH_DRAFT.md:1374`）。
- 技术稿提出“流星雨 + 援军”两地图法术（`TECH_RESEARCH_DRAFT.md:1378`），与指定参考作品的高辨识度组合过近。
- `TowerData` 仍包含 Kingdom Rush 式 Tier 4 分叉字段（`TECH_RESEARCH_DRAFT.md:803`、`:854-856` 附近），同时另一节又说简化为三档（`:1375`）。
- PRD 已明确要求不要复刻塔盘、技能图标和布局（`PRD_FRAMEWORK_DRAFT.md:568` 附近），但资产稿推荐木质/卷轴中世纪 UI（`ASSET_AUDIO_RESEARCH_DRAFT.md:187-194`），容易回到同类作品的常见表达。

**影响**

即使法律上没有逐项复制，市场第一印象仍可能是“免费素材拼装的 Kingdom Rush 仿作”，削弱品牌、商店转化和口碑。

**必须修订**

- 删除技术稿中传统四塔、流星雨、援军、KR 分叉字段；
- 用 PRD 六塔和航标充能系统重写技术接口；
- 为六塔、四英雄、四章节、六 Boss 各建立“轮廓差异证明”；
- UI 采用航海仪器、潮汐刻度、棱镜/余烬机械语言，不能使用默认木牌卷轴作为主视觉；
- 宣传、图标和商店截图不得依赖“像某游戏”解释价值。

**放行标准**

把 Logo 隐去后，让 10 名目标玩家看 5 秒战斗截图；至少 7 人能描述“潮汐/航标/线路塔”等本作特征，而不是只回答“像某经典塔防”。

## B-04 技术稿没有覆盖 PRD 的独有系统，无法指导完整实现

**缺失或不足**

1. 明暮相位状态机、相位时间轴、提前/延后、路线切换和 Boss 锁定；
2. 六塔三模块、IV 级主动、链接塔、双桩塔、碎片经济；
3. 英雄移动、倒地复归、四技能、天赋、自动施放辅助；
4. 航标充能在英雄终极技和地图装置之间的竞争；
5. 战役地图、24 关解锁、航标印记、三棵成长树、免费重置；
6. 四难度与独立辅助参数；
7. 图鉴、30 成就、本地/Steam 幂等对账；
8. 完整无障碍设置、手柄焦点、字幕与低视觉噪声模式；
9. 本地化 key、复数/变量、伪本地化和 CJK 字体回退；
10. PRD 版本化 DTO、三份轮转备份、最近五版迁移测试；
11. 固定种子、战报统计、平衡快照和批量模拟器；
12. 章节 Boss 阶段检查点和战斗中断恢复策略。

技术稿目前主要停留在通用 `EnemyBase`、`TowerBase`、`WaveManager`、投射物和 JSON 示例，且示例仍使用 goblin、gold、lives、三档塔等旧概念。

**影响**

它可以帮助完成 P1 骨架，却无法连接到完整产品。后续每个 agent 都会自行发明接口，造成系统各自可运行、合起来不可维护。

**必须修订**

在正式编码前产出 `TECHNICAL_DESIGN.md`，为上述 12 项逐一给出：责任节点/服务、Resource schema、运行时状态、信号/命令、保存字段、错误状态、测试入口和性能预算。

**放行标准**

PRD 第 27 节列出的后续文档中，至少先完成正式技术设计、关卡规范、平衡表、资产风格指南、QA 计划和里程碑 backlog；不能把“以后拆分”当作当前已可执行。

## B-05 资产稿只是候选网站清单，不是完整游戏资产生产方案

**证据**

- 资产稿自认严格俯视塔素材稀缺，需要自绘或改造（`ASSET_AUDIO_RESEARCH_DRAFT.md:27`）。
- P0 简体中文需要字体，但所有首选字体均无 CJK，且文档将其排除在本次范围外（`:28`）。
- 推荐组合同时出现 16×16 与 32×32 地形（`:17`、`:53-65`），PRD 又尚未在 16×16/24×24 中冻结角色规格（`PRD_FRAMEWORK_DRAFT.md:583`）。
- 候选敌人是通用地牢怪、史莱姆、僵尸、蜘蛛和飞行射击素材，塔候选甚至包含坦克/车辆改造（`ASSET_AUDIO_RESEARCH_DRAFT.md:78-168`），与潮汐群岛、孢潮、沉钟、航标等正式内容没有一一映射。
- 没有覆盖 4 名英雄、24 普通敌人、8 精英、6 Boss、六塔四级外观、18 个塔模块、技能图标、章节机关、战役地图、剧情演出、成就图标、商店胶囊和宣传截图。

**影响**

免费资产足以做灰盒和部分环境，却无法支撑成品的一致轮廓、角色辨识、章节递进与营销画面。后期整体换皮的成本可能接近重新制作全部内容。

**必须修订**

将资产稿升级为“资产生产矩阵”，每项对应稳定内容 ID，并记录：

- 数量、尺寸、方向、帧数、调色板、光向、轮廓、挂点、导出格式；
- 候选来源、正式来源、需改造比例、人工工时、许可证状态；
- 灰盒/纵向切片/Alpha/Beta/RC 的完成度；
- 同屏可读性和低特效替代版本；
- 中英字体、fallback、UI 图标和营销素材。

**放行标准**

纵向切片 C01–C03 的全部正式资产能够列成 100% 可勾选清单，且至少做出一张接近最终品质的战斗截图和一段 30 秒战斗录屏，证明资产能形成统一世界，而非仅在法律上可以混搭。

## B-06 许可证结论过度确定，不能直接作为商用放行依据

**证据**

- 文档开头说“所有条目均经联网核实”，但同时承认多个 itch.io 原始页面无法访问，只做间接核实（`ASSET_AUDIO_RESEARCH_DRAFT.md:6`、`:71`、`:79`、`:111`、`:161`、`:256`、`:461-465`）。
- “全部 CC0 素材之间任意混搭，零冲突”是过宽结论（`:417`）；许可证兼容不代表商标、人格权、素材内容来源或风格不存在风险。
- “CC-BY-SA 会传染衍生作品，与闭源商用发行冲突”被写成绝对法律结论（`:423`）。即使项目决定一律排除以降低风险，也应写成项目政策，而不是未经法律复核的普遍事实。
- Sonniss 等专有 EULA 条款可能变更，文档虽有提醒，但“可混用合法”仍写得过于确定（`:370-383`、`:420`）。

**影响**

零基础用户会把“推荐 S”“已核实”理解成发行许可。若下载包内许可证、网页条款、作者身份或素材内容与研究时不同，项目承担实际风险。

**必须修订**

- 将状态拆为：`候选`、`原页已核`、`下载包 LICENSE 已核`、`归因文本已生成`、`发行白名单已批准`；
- 间接核实资产不得进入发行白名单；
- 下载时保存原始压缩包 hash、许可证原文/PDF、页面截图和日期；
- 将 CC-BY-SA/GPL 等条款改写为“本项目风险政策：为降低复杂度，v1.0 不采用”，不要冒充法律定论；
- 最终发布前由具备资质的人复核高风险 EULA 和商标问题。

**放行标准**

发行构建中的每个第三方文件都能由路径反查到台账、许可证证据、归因文本和批准状态；任何“间接核实”“待复核”资产数量为 0。

## B-07 工期和产能估算不可信，容易诱导错误承诺

**证据**

- PRD 估计零基础用户、agent 主力、兼职投入 15–24 个月（`PRD_FRAMEWORK_DRAFT.md:910`）。
- PRD M0–M6 给出的区间相加约为 54–83 周，尚未显式加入审批等待、返工、假期、外包沟通和完整发布维护。
- 技术稿给 0 基础、每周 15–20 小时的计划却只有约 36–54 周到“可发布”，并只预算 8–12 关（`TECH_RESEARCH_DRAFT.md:1342-1352`）。
- PRD 的正式范围包含 24 关、六塔多模块、四英雄、38 类敌/Boss、两种语言、完整 UX/无障碍/Steam/QA；资产稿又确认塔、CJK 字体和动画存在缺口。

**判断**

Agent 可以加速样板代码、表格、验证器和重复性工作，但不能免除游戏手感、关卡调优、视觉统一、许可证、外测和返工。15–24 个月可作为有经验小团队或大量外包支持下的进取目标，不应作为零基础兼职个人的基准承诺。

**必须修订**

用工作量而不是日历愿望估算：

- 每项系统、关卡、敌人、塔、英雄、UI 页面、动画、音频、本地化和测试列人时区间；
- 单独计入 30%–50% 集成/返工缓冲；
- 记录“人类必须完成”的工时，不把 agent 生成时间等同于验收时间；
- 用纵向切片实测吞吐重新预测 24 关完成日期。

**建议的诚实基线**

在不缩成 Demo、仍保留四章完整结局的前提下：

- 零基础、兼职 15–20 小时/周、主要使用现有资产并少量委托：先按 **30–48 个月**风险区间管理；
- 若希望维持 18–24 个月，需要接近 1.5–2 个全职当量，或明确的美术、音频、QA、本地化外包预算；
- 以上只是制作规划假设，必须在纵向切片后按真实吞吐重估，不能写成事实。

**放行标准**

纵向切片完成后，拿实际耗时计算“每关灰盒/正式美术/调优/回归”“每敌人/塔/英雄”的中位工时；24 关预测完工日期及 50% 缓冲必须仍在项目主理人可接受范围内。

---

## B-08 技术稿把未经充分核验的推断写成“事实”

**高风险示例**

- `TECH_RESEARCH_DRAFT.md:53-64` 将 Godot 4.7 名称、日期、支持等级和功能打包写成“当前最新稳定”，但给出的主要链接并不能在文档内部逐条证明全部结论；“4.7 LTS 风格稳定线”也不是一个清晰的官方支持承诺。
- `TECH_RESEARCH_DRAFT.md:399` 直接以 Google 搜索综合页作为 Navigation API“事实”来源。
- 多处以博客、论坛、技能聚合页或截断 URL 支撑“业内事实”（例如 `:332`、`:446`、`:537`、`:1110`）。
- `TECH_RESEARCH_DRAFT.md:1072` 把 Web 音频支持写成绝对结论；这类平台/浏览器/导入规则必须按锁定 Godot 版本和导出模板实际验证。
- `TECH_RESEARCH_DRAFT.md:1194-1203` 对 GUT 版本兼容性给出精确推荐，但未提供可复现的安装锁定与测试证据。
- `TECH_RESEARCH_DRAFT.md:1265-1313` 的平台能力、商店费用和发行建议均可能随时间变化，不应作为永久常量。
- PRD 的 `[R1]`–`[R11]` 只是来源名称索引，没有具体链接、版本、页面标题、访问快照和“哪句话由哪个来源支持”的可审计关系（`PRD_FRAMEWORK_DRAFT.md:1195-1218`）。

**影响**

零基础用户通常无法识别 API 错误、过期配置或行业观点；agent 会把“事实”复制进代码和后续文档，形成权威幻觉。

**必须修订**

建立事实等级：

- **Verified**：锁定版本的官方文档/源码/本地可复现实验；
- **Observed**：本项目 spike 或测试机实际结果；
- **Assumption**：尚未验证的计划假设；
- **Recommendation**：设计/工程选择；
- **Policy**：项目为了风险控制主动采用的规则。

每个版本敏感结论记录：版本号、访问日期、具体页面、验证命令或最小工程。社区资料可以帮助发现问题，但不能单独支撑“必须”“唯一”“当前事实”。

**放行标准**

所有影响架构、许可证、平台和发行的事实都有官方来源或本地 spike 证据；无法验证的内容明确降级为假设，不进入 agent 的强制约束。

## B-09 缺少可供 agent 安全执行的正式生产 backlog 和变更治理

**现状**

PRD 第 23 节提出了 agent 任务应包含唯一写入范围、稳定 ID、测试和变更报告，这个原则正确；第 27 节也列出 13 份后续文档。但当前三份草案仍没有：

- 全项目依赖图和关键路径；
- 每个任务的输入/输出接口；
- canonical schema 与生成代码的边界；
- 代码所有权与并行写入规则；
- golden level / golden save / golden screenshot；
- 自动数据校验、资源白名单和本地化门禁；
- PRD 变更流程与旧 ID 迁移流程；
- “agent 完成”到“人工批准”的状态机；
- 零基础用户每一步应执行的命令、预期结果和失败恢复。

**影响**

Agent 会“完成很多文件”，但项目主理人无法判断是否在正确方向，多个 agent 也会在同一模块产生竞争实现。

**必须修订**

在 M0 结束前建立版本化 backlog，每个任务必须包含：目标、非目标、只写文件、依赖、接口、测试、截图/录屏验收、性能预算、存档影响、许可证影响、人工批准人和回滚方法。

**放行标准**

零基础用户只按照任务卡执行，可以从空工程得到 C01 灰盒；任何一步失败时有明确诊断，不需要自己发明架构或让 agent 自行扩大范围。

# 3. Major — 会造成显著返工或成品不足

## M-01 愿景有机制，但缺完整的叙事与情感交付规格

PRD 有“暮潮群岛、迁徙舰队、守潮者”等强概念，却没有冻结：玩家身份、核心冲突、四章剧情转折、四英雄关系、Boss 动机、结局状态、关前/关后叙事载体、文案量和过场资产量。24 关容易变成机制列表，而不是完整战役。

**建议**：制作 3–5 页 Content Bible，规定世界规则、阵营、章节弧线、语气、禁用陈词、每关叙事功能、结局和文本预算。不要扩大成 RPG；每关 2–4 条简报、Boss 前后短场景和章节插图即可形成完整情感闭环。

---

## M-02 相位系统仍是创意框架，尚未变成可生产规则

PRD 列出明暮可以改道路、节点、敌人形态、塔职能和机关，但没有给 24 关逐关的准确相位脚本、切换次数、预告、保存/暂停行为、敌人在切换瞬间的位置迁移规则、相位仪与 Boss 锁定冲突规则。

**建议**：建立 `PhaseEventData` 与 24 关相位矩阵。单关逐项标出“变化前/后路线、受影响实体、预告秒数、可否干预、失败恢复、测试种子”。先把 C02、C04、C11、C20、C24 做成五种标准模板。

---

## M-03 塔和英雄的组合复杂度没有进入制作预算

六塔 × 三模块 × 四等级，再叠加链接、碎片、双桩、主动技能、四英雄技能和成长节点，会形成大量交互。PRD 给了模块选择率指标，却没有完整技能效果优先级、乘区、叠加、复制、免疫和冲突表。

**建议**：建立 Combat Rulebook：伤害顺序、状态唯一性、塔链接图、主动复制白名单、控制递减、Boss 转换、伪随机和四舍五入顺序。每个新技能必须列出与全部现有系统的交互矩阵。

---

## M-04 平衡模型有理论，没有首个可玩的完整数值版本

PRD 的伤害公式、威胁预算、DPS 指数和目标胜率有价值，但“指数”无法直接生成 C01；技术稿则仍使用 HP=100、伤害=10 等教程数值。缺少：六塔四级成本/伤害表、24 敌基础表、C01–C03 逐波预算、英雄一级技能倍率、成长节点成本和难度修正后的实际结果。

**建议**：在编码前先交付 Balance v0.1，至少让 C01–C03 可以完全由数据生成。之后实现 headless batch simulator，输出胜负、漏怪、经济、塔伤害、控制贡献和关键波次。

---

## M-05 24 关蓝图尚不足以指导关卡制作

当前表格给出路线数量、机制和新内容，但没有地图尺寸、路线长度、重叠覆盖、建造点坐标、入口时间、逐波组成、相位时间、目标条件、预期经济、推荐/禁用内容和性能上限。Agent 仍需自行做关卡设计，而不是执行已批准设计。

**建议**：为每关制作一页 Level Brief；C01–C03 必须先达到逐波规格，其他关可先保留蓝图。每关至少包含 2 个候选布局和 3 套标准难度通关记录。

---

## M-06 战役成长仍有潜在刷取与难度污染

PRD 一方面反对刷取，另一方面允许英雄重复通关获得递减经验；未定义递减公式、等级门槛、落后英雄追赶和满级时点。三棵成长树也未给节点成本和对关卡基线的具体影响。

**建议**：英雄成长以首次主线进度为主要来源，重复关卡只提供极小补偿或不提供战力；明确“首次通关主线时英雄等级区间”。所有关卡至少用“无成长基线”和“典型成长基线”各验证一次。

---

## M-07 UX 要求完整，但没有线框、焦点图和状态设计

PRD 已列 HUD 信息位置、缩放和输入要求，但还不足以实现：

- 建塔/升级/模块选择在鼠标与手柄下的完整流程；
- 暂停、教程、敌人卡、战报之间的层级；
- 焦点丢失、手柄断线、分辨率变化、文本扩长；
- 存档损坏、云冲突、磁盘满、设置恢复；
- 640×360 下中文、计时轴、四技能和塔面板是否同屏可读。

**建议**：纵向切片前交付 10–15 张低保真线框、手柄焦点路径和关键错误态。640×360 是假设，必须用 CJK、160% UI 和 16:10/21:9 实图验证后再冻结。

---

## M-08 中文字体是首发阻断风险，却被资产稿后置

PRD 的 P0 是简中和英文；资产稿明确首选字体没有 CJK，却说不在本次范围（`ASSET_AUDIO_RESEARCH_DRAFT.md:28`）。字体会影响逻辑分辨率、文本框、按钮、数字基线和像素风格，不能在 Beta 才补。

**建议**：M0 就锁定一套可商用 CJK 正文字体、一套拉丁显示字体和 fallback 策略；标题可以像素化，正文优先可读性，不应强制使用 Press Start 2P/VT323 承担长文本。

---

## M-09 美术没有风格圣经，推荐等级主要按许可证而非产品适配度

资产稿的 S/A/B 评级把“许可安全、能下载”与“适合本作正式画面”混在一起。Kenney Tiny、Buch 32px、0x72、Spine 僵尸、坦克塔、木卷轴 UI、扁平粒子并不天然组成统一画面。文档虽然承认不宜混搭，却仍在总推荐表中并列。

**建议**：拆成两个评分：`License Confidence` 与 `Art Fit`。先锁定像素密度、投影视角、色板、描边、光向、饱和度、动画帧率和材质语言，再重新评级。正式英雄、塔、Boss 和 UI 主视觉原则上需要原创或高强度重绘。

---

## M-10 音频清单没有形成声音身份与事件覆盖

当前音乐主要是零散 chiptune，SFX 是大型通用包。没有定义本作应是纯 8-bit、现代像素混合、海潮机械、玻璃孢光还是钟声氛围；也没有把 PRD 的飞行、隐匿、治疗、相位预警、出口告急、六塔技能、四英雄和六 Boss 映射到声音事件。

**建议**：建立 Audio Event Matrix 和 3 条标志性声音支柱。每章至少有探索层/战斗层/Boss 动机，关键威胁必须听觉可辨；通用包只作为原材料，需统一响度、采样质感、尾音和空间感。

---

## M-11 发布平台策略不统一并发生隐性扩张

PRD 只承诺 Windows，预留 Linux/Steam Deck；技术稿却同时设计 macOS、Android、iOS、Web、Steam Deck，还给出各平台导出建议（`TECH_RESEARCH_DRAFT.md:1263-1324`）。性能目标甚至包含“主流安卓机”（`:1103`）。

**建议**：M0 只验证 Windows；Beta 再验证 Steam Deck/Linux 是否进入 v1.0。移动/Web/macOS 均作为独立商业决策，不要因为引擎“可以导出”就把它们加入工程约束。

---

## M-12 发行策略与“完整买断制”定位冲突

PRD 定义买断制完整单机；技术稿建议 itch.io 测试版、Steam EA，甚至“考虑 Demo / EA”（`TECH_RESEARCH_DRAFT.md:1313`、`:1351`）。Demo 可以是营销切片，并不等于缩小正式版；EA 则会改变承诺、存档兼容、内容节奏、社区维护和评价风险。

**建议**：明确选择：

- 推荐：内部/封闭测试 → 可选公开免费 Demo → 完整 v1.0 买断发布；
- 只有在现金流或社区共创是明确商业策略时才使用 EA，并新增 EA 内容承诺与维护计划。

---

## M-13 存档没有决定“40 分钟关卡中断恢复”

PRD 主要在结算和成长变更时自动保存，但后期关卡目标时长可达 40 分钟，C24 还有多 Boss 阶段。仅有 Boss 阶段重试并不能解决退出游戏、断电或系统休眠。

**建议**：明确是否支持单局 suspend save。推荐在波次结束和 Boss 阶段点保存一次临时战斗快照，加载后删除或继续；快照包含随机种子、波次、经济、完整度、塔/英雄/相位状态。必须防止跨版本损坏并提供放弃本局。

---

## M-14 无障碍目标有价值，但需要技术可行性分层

PRD 的字幕、色弱、重绑定、低特效、独立辅助均适合 P0；屏幕朗读语义和焦点顺序被放入 P1，但技术稿没有任何实现路线。若最终不支持屏幕阅读器，不应通过“预留”制造虚假承诺。

**建议**：拆为：确定支持、实验支持、不承诺三类；为每项指定实现、测试者和验收设备。任何商店宣传只写已经由真实用户完成任务流验证的功能。

---

## M-15 缺少商业与市场验证闭环

完整可发布不只等于代码和内容完成。当前没有明确：价格区间假设、竞品定位、商店标签、愿望单节奏、宣传片/胶囊图生产、试玩反馈问题、可退货首小时体验、媒体/主播构建、发布时间窗口和上线后补丁容量。

**建议**：增加轻量商业计划，不要求做在线运营。纵向切片完成后制作商店级截图测试定位；Alpha 期间建立 Steam 页面；Beta 前冻结价格、标签、支持语言和功能声明。

---

## M-16 缺少内容评级、隐私和崩溃数据决策

PRD 默认不上传遥测，但又提到崩溃收集；未定义玩家同意、收集字段、保存期限和离线行为。敌人死亡、闪烁、恐怖元素、酒精/血液等内容评级也未列。

**建议**：在内容圣经加入分级目标和禁用内容；若使用崩溃服务，建立独立隐私说明、显式开关和最小化字段。完全离线也是可接受选择。

---

# 4. Minor — 一致性与维护性问题

## N-01 P0/P1/P2 术语重载

PRD 用 P0/P1/P2 表示发布优先级，技术稿用 P0–P5 表示阶段。Agent 很容易把“发布后 P2”误解为“第二阶段必须完成”。

**建议**：优先级改为 Must/Should/Later；阶段统一用 M0–M7。

## N-02 术语仍混用旧原型名称

技术稿使用 `gold`、`lives`、`Stars`、`goblin_grunt`、`archer_basic`，PRD 正式术语是火种、舰队完整度、航标印记和原创敌塔 ID。

**建议**：建立双语术语表和禁用旧词扫描器。

## N-03 塔等级数据相互矛盾

技术稿代码默认 `tier_count = 3`，PRD 是四级；技术稿退款比例 0.6，PRD 是 0.7；技术稿同时存在分支字段和“无分支”结论。

**建议**：研究代码只标“示意”，正式 schema 从 PRD 自动生成或复制稳定字段，不保留第二套默认值。

## N-04 “完整商业级原型/独立游戏”表述含混

`ASSET_AUDIO_RESEARCH_DRAFT.md:4` 同时使用“完整商业级原型”和“独立游戏”。原型和正式发行的资产验收完全不同。

**建议**：分别标记 Prototype-only 与 Shipping-approved。

## N-05 参考来源缺少可复现快照

三份文档中的网页未来可能变化或失效；部分链接是搜索页、聚合页或不完整 URL。

**建议**：正式研究台账记录页面标题、访问日期、内容 hash/截图和本地许可证副本。

## N-06 成就不应把无障碍设置变成形式化打卡

PRD 中“使用色觉预设完成关卡”等成就虽然语气友善，但可能鼓励玩家短暂切换设置刷成就，也可能把辅助功能当作内容消费。

**建议**：保留“自己的节奏”作为无奖励引导提示，平台成就更适合聚焦玩法和进度。

## N-07 缺少统一状态词

草案中同时出现 Draft、候选、推荐 S、P0、正式、发布必需、待复核，没有统一生命周期。

**建议**：统一为 `Research → Proposed → Approved → Implemented → Verified → Shipping`。

## N-08 缺少素材派生文件规则

资产稿记录源文件，但没有规定裁切、调色、导入、压缩后派生文件如何关联原始许可和源 hash。

**建议**：派生资产 metadata 保留 `source_asset_id`，Credits 从台账生成。

## N-09 过多“必须”没有责任人

技术稿对对象池、渲染器、音频格式等给出大量绝对命令，却没有验证任务或负责人。

**建议**：把“必须”限制为已经批准且有测试的项目约束，其他改为 spike 假设。

## N-10 文档没有变更记录

三份均为草案，但没有版本历史、批准人、冲突决议和废弃章节标识。

**建议**：每份正式文档增加 changelog、owner、approver、依赖版本和 supersedes 字段。

## N-11 目标硬件仍不可购买式描述

“主流集显/四核机器”“中端 PC”无法测试。

**建议**：选定至少一台最低规格、一台推荐规格和一台 Steam Deck 类设备，记录 CPU/GPU/RAM/OS/分辨率。

## N-12 纵向切片与 Demo 概念需要区分

内部纵向切片是验证完整生产链，不等于对外 Demo，也不等于缩小最终游戏。当前技术稿反复使用 MVP/demo，容易让用户误以为目标被偷换。

**建议**：统一称“发布质量纵向切片”；对外 Demo 是后续商业交付，必须单独决策。

# 5. 关键遗漏决策清单

以下决策在冻结前，agent 只能做可丢弃 spike，不能批量生产正式内容：

| 决策 | 当前冲突/缺口 | 推荐默认 |
|---|---|---|
| 唯一范围 | 24 关 vs 8–12 关 | 保留 PRD 的 24 关目标；若风险触发，允许压到 20 关但仍保持四章、完整结局和正式品质 |
| 路径模型 | 固定节点 vs 自由堵路 AStar | 固定 BuildNode + 预制 PathNetwork |
| 塔结构 | 六塔四级三模块 vs 四塔三档/分支 | 六塔、四级、II 级三选一模块 |
| 英雄结构 | 四技能 vs 一主动一被动 | PRD 四技能结构；用统一 SkillData 控制成本 |
| 地图主动 | 航标充能/潮汐仪 vs 流星雨/援军 | 删除后者，保留原创充能竞争 |
| 首发模式 | 战役 vs 战役+无尽/EA | v1.0 完整战役；无尽 P2；EA 单独商业决策 |
| 像素规格 | 16、24、32 混用 | 纵向切片实测后锁一个世界单位；UI 可独立分辨率但需统一光向/色板 |
| UI 视觉 | 潮汐仪器 vs 木质卷轴 | 潮汐航海仪器语言 |
| CJK 字体 | P0 需要但未选 | M0 锁定可商用可读字体 |
| 路线保存 | 仅结算存档 | 增加波次/阶段 suspend save |
| 平台 | Windows vs 全平台 | Windows P0；Linux/Deck 条件进入；其他后置 |
| 遥测 | 默认不收集 vs 崩溃收集 | 默认离线；崩溃上传需单独同意 |
| 美术来源 | 免费包混搭 vs 原创品牌 | 环境可合规改造；塔、英雄、Boss、UI 主视觉优先原创/委托 |
| 生产工期 | 15–24 月 | 纵向切片后按实测吞吐重估；项目管理先采用更保守风险区间 |
| 法务状态 | “推荐 S”即安全 | 只有发行白名单状态可进入 shipping build |

# 6. 不缩成 Demo 的修订后阶段策略

这里的核心原则是：**先验证生产链，不削弱完整游戏承诺；纵向切片是第一批正式内容，不是做完就停止的 Demo。**

## Gate A：产品统一与事实清理（3–6 周）

交付：

- 唯一真相表和术语表；
- 正式 PRD v1.0；
- PathNetwork、塔/英雄/技能、存档与相位技术设计；
- 美术风格圣经、CJK 字体与许可证白名单流程；
- 24 关内容矩阵和人时预算；
- 事实/假设/政策分级后的研究稿。

退出标准：本审查全部 Blocker 有 owner、修订文件和验证证据；三份文档不再描述不同游戏。

## Gate B：发布质量纵向切片 C01–C03（建议按实际工作量估时）

必须是正式生产链：

- 六塔中至少三塔达到正式质量，其中每塔至少两个模块可玩；
- 一名完整英雄；
- 6–8 个正式敌人；
- 两种相位模板；
- 中英、本地化 key、CJK 字体、键鼠/手柄、无障碍基础；
- 正式存档、设置、教程、战报、音频混音；
- 自动测试、性能压力场景、许可证台账；
- 一张商店质量截图和 30 秒录屏。

退出标准：新手盲测、目标机性能、存档迁移和资产一致性全部达标。通过后这些内容直接进入 v1.0，不丢弃。

## Gate C：第一章完整生产 C04–C08

重点不是新增系统，而是验证内容吞吐：

- 六塔、两英雄、第一章敌人与 Boss 1 完成；
- 建立关卡模板、波次编辑/校验、平衡报表；
- 实测每关和每实体人时；
- 重新预测完整 24 关日期和预算。

退出标准：连续三关能在预测工时 ±25% 内完成；若不能，先优化工具和复用，不立即牺牲完整度。

## Gate D：全战役 Alpha C09–C24

按章节生产，不同时打开所有关卡：

1. 第二章灰盒→调优→正式资产→回归；
2. 第三章同流程；
3. 第四章及终局；
4. 每章结束后进行完整新档测试。

退出标准：24 关从新档可完整通关；不要求所有演出最终化，但核心系统、成长、结局与保存不可再缺。

## Gate E：Beta / 内容锁定

只允许修复、调优、资产替换、本地化、无障碍和性能工作；禁止新增无尽模式、编辑器、平台和新塔。完成 30 成就、商店素材、许可证、云存档和外部测试。

## Gate F：发布候选与首月

完成安装/升级/离线/Steam 对账/损坏档/手柄/多分辨率/两语言/低端机矩阵；保留至少 4 周发布缓冲和首月热修复容量。

# 7. 建议的跨文档修订顺序

1. **先修 `PROJECT_CANON` / PRD**：冻结产品，不写代码；
2. **再重写技术稿**：删除通用 KR 骨架冲突，覆盖相位、固定路线、六塔、英雄和战役；
3. **再写 Art Style Guide**：冻结规格后重评资产，不能反过来让免费素材决定世界观；
4. **建立 Balance v0.1 与 C01–C03 Level Brief**；
5. **建立可执行 milestone backlog**，任务带接口和验证；
6. **最后开始 Godot 工程和纵向切片**；
7. 纵向切片通过后才批量制作 C04–C24。

错误顺序是：下载大量免费资产 → 做通用四塔框架 → 做 8–12 关 → 后期尝试塞入相位、英雄、手柄、中文和 24 关。该路径极可能产生结构性返工。

# 8. 最终放行门槛

只有同时满足以下条件，才可判定“这些文档真的能指导零基础用户和 agent 完成完整塔防”：

- [ ] 所有 Blocker 已关闭，且有文件与测试证据；
- [ ] 三份正式文档使用同一内容数量、术语、ID 和系统结构；
- [ ] 固定路线/相位网络已用 C02 验证；
- [ ] C01–C03 有逐波、逐点位、逐资产、逐 UI 状态的生产规格；
- [ ] 六塔、四英雄、全部敌人/Boss 均进入资产和技术矩阵；
- [ ] CJK 字体、手柄、无障碍和存档从纵向切片开始实现；
- [ ] 所有第三方资产进入可审计发行白名单；
- [ ] 事实、假设、建议和项目政策明确分级；
- [ ] 有按真实人时计算的 24 关计划和缓冲；
- [ ] Agent backlog 对每个任务规定唯一写入范围、接口、测试和人工验收；
- [ ] 纵向切片是 v1.0 的正式前三关，不是交付后停止的 Demo；
- [ ] 即使砍 P1/P2，仍然保留四章、完整成长、完整结局和可发布质量。

## 9. 审查结语

`PRD_FRAMEWORK_DRAFT.md` 已经接近一份优秀的“完整游戏设计宪章”，最大的价值是没有用 MVP 偷换完整产品目标，并且提前考虑了失败可解释性、无障碍、存档、测试和 IP 风险。

但技术稿和资产稿仍然主要服务于一个传统、通用、低内容量的塔防原型。当前真正需要做的不是继续增加更多点子，也不是立刻写代码，而是把三份文档压缩成一套**无冲突、可审计、可逐任务执行的正式生产规格**。

最终判断：

- **能否指导做出塔防原型：能。**
- **能否在当前状态下可靠指导零基础用户与 agent 做出 PRD 所承诺的完整正式版：不能。**
- **是否需要把范围缩成 Demo 才能继续：不需要。**
- **正确动作：保留完整游戏目标，先关闭 Blocker，用发布质量纵向切片验证生产链，再按章节完成全部战役。**
